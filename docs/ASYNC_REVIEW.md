# 终局复盘怎样减少等待

更新于2026年10月31日。目标是先让玩家看到赛果，再逐步看到复盘，不让整个页面等模型返回。

## 原来慢在哪里

旧自动复盘和复杂追问走同一条工具循环：先问模型要看什么，读记录，再问模型，有时还继续查。多次远程往返结束前可能没有正文，主页面又同步等待，玩家就感觉卡住了。

另外，完成时整页重绘、撤掉临时输出位置，曾让刚显示的文字短暂消失。速度和正文保留是两类问题，不能只修其中一个。

## 现在分成两条路

**自动复盘用短路径。** 程序读取整局、关键回合和最多两个回合详情，再让模型总结。工具记录标明由程序选取。最多两次模型生成或修正，四十秒预算，自动复盘不先做换招模拟。

**深入追问保留工具Agent。** 玩家问“第二回合换一招会怎样”时，模型仍可以按问题选择工具、读取结果、继续查证。这类问题不必为追求短等待而删掉实际查证。

## 页面怎样保持可操作

1. 先显示赛果、生命和回合记录。
2. 冻结这局的输入快照，把复盘交给后台线程。
3. 页面定时读取进度。读工具时显示实际进度，收到正文后真实流式显示，不把完整文本拆字假装生成。
4. 完成后保存正式复盘和学习事件，在同一个页面片段保留正文。
5. 失败时保留已显示草稿，标记未完成，允许重试。

同一任务按对局与模式复用，刷新不会重新发起一套调用；同一复盘只保存一次。线程不直接修改Streamlit界面。普通聊天的失败保留另见[消息生命周期](RESPONSE_LIFECYCLE.md)。

## 有没有实测

一次真实合成样例中，首段正文1.490秒，最终核验10.331秒。较早的一次样例为16.580秒和20.747秒。两次调用时刻和路径不同，只能说明实现及案例变化，不能宣称稳定加速多少倍或P95达到多少。

还保留了未约束JSON格式时的失败：两轮修正没能完成。之后补齐结构化输出要求再复验，不把失败记录改成成功。

原始记录见[真实复盘证据](async-review-prefetch-json-live-evidence.json)。模拟延迟的页面测试验证完成、失败和多次定时刷新后正文仍在，二者用途不同。

## 当前限制

最多两个工作线程，不是生产任务队列。服务重启会丢内存中的任务，已经保存的赛果不丢；提前离开旧局后，旧任务仍可能运行，正式结果需要回到对应页面收集。没有离页可靠保存或跨进程恢复。

结构化输出成功也不等于解释正确。实际样例仍有过度概括等问题，下一步应独立评审内容，同时测延迟分布和用量。当前完整结果见[VALIDATION](VALIDATION.md)。
