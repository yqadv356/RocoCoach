# Agent怎样理解请求并真正执行

更新于2026年10月31日。核心原则：模型决定要做什么，应用程序检查能不能做、是否做成，再保存和反馈。入口是[match_chat](../rococoach/match_coach.py)。

## 先看一个例子

玩家说“再来一局难一点的”。系统先读当前对局和最近对话，让模型判断这是开局请求、讨论，还是对前面提议的确认。确认要执行后，程序核对场景和档位，创建真实新局，检查它是第1回合、配置正确，再写入数据库。保存成功后才告诉玩家新局已开始。

如果玩家说“再解释一次”，就应该继续讲解，不能因为有“再来”就重开。旧版本靠短语筛选，容易漏掉或误判；现在在线操作统一走结合上下文的语义计划。离线演示仍有有限规则，和真实模型路径分开。

## 有两种执行方式

| 请求 | 怎么处理 | 谁决定工具 |
| --- | --- | --- |
| 赛后查某回合、比较另一招 | 模型选工具，程序执行并返回结果，模型再查或回答 | 模型；使用原生Function Calling |
| 开新局、改讲解风格 | 模型给结构化计划，程序核对并执行 | 模型提出计划；程序掌握写入权 |
| 自动整局复盘 | 程序先读整局和必要回合，再让模型总结 | 程序；记录中明确标注 |

结构化计划叫IntentPlan：把“想做什么、是不是当前要执行、指向哪个方案、使用什么参数”放进固定字段。得到计划只代表理解结果，不代表操作已经执行。

## 模型能改什么

- `start_new_match`：使用四个已有场景、标准或进阶档位开新局，保留旧局。
- `set_response_style`：保存简洁、详细或引导式的明确偏好，不改变对局。
- `propose_new_match`：保存待确认方案，本身不开局。

没有任意代码、SQL、自由档案写入或代玩家出招的能力。参数只能来自现有选项。对局中的公开观察和赛后详细计算也按阶段分开检查。

## 怎样承接“就按这个来”

新提议保存方案编号、参数、提出时的对局状态和五分钟有效期。下一条确认要和这个方案对应；话题变了、方案过期或局面变了，就不执行旧提议。兼容旧文本提议时，会绑定最近完成的助手消息并再次核对。

这里靠的是语义和已保存方案，不是把“好的”当成永远有效的开局命令。替换未结束整局还多一次语义核对，区分重讲、再试行动和重开。这次核对仍由同一模型服务完成，也可能出错。

## 怎样保证操作真的做成

[control.py](../rococoach/control.py)负责执行与保存：

1. 检查操作、参数和当前状态是否匹配。
2. 实际创建候选新局，核对新编号、零回合、未结束、场景、档位和规则版本。
3. 用请求编号防止同一请求重复创建，这叫幂等。
4. 在一次SQLite事务中检查规划期间局面是否变化，合并期间新增的消息，再保存。事务让这次操作整体成功或整体失败，避免只改一半。
5. 根据已保存的结果反馈成功；失败不提前宣布完成，也不回退成关键词自动操作。

状态token是当前对局的核对标记，用来发现旧计划，不是账号登录令牌。它不能代替用户语义判断。

## 工具循环为什么要有上限

赛后查证最多五次模型请求、八次工具、七十五秒预算。每次调用都检查阶段和参数，失败会作为实际观察返回。预算防止反复查证拖得太久，但阻塞网络读取仍受SDK超时影响，不是精确到秒的硬中断。

单回合换招重放使用真实引擎，主局不变；它只说明一个固定种子的样例，不能当胜率。实际工具和结果可查看，模型隐藏思考不展示。

## 进阶实际改变什么

标准对手随机选合法招式；进阶按公开局面计算“直接伤害区间均值×标称命中率”，选分数最高的可用行动。不偷看玩家本回合选择，不改血量、攻击或随机数。未指定场景时使用均衡镜像对练。

它还不会完整规划状态技、资源和多回合目标，不能叫最优战术，也不保证每局更难。没有Agentic RL或多Agent。

## 怎样验证

两例真实千问请求实际创建并保存了进阶新局；网页还验证了确认后开局和刷新保持。14题真实语义探索两轮各13/14，保留含糊重试误判，没有把已知题调成通用准确率。

程序回归另测重复提交、过期待办、状态冲突、失败不半写等。每条人工消息会多一次规划调用，探索样例约一至三秒，这是当前代价。原始记录和当前测试结果统一见[VALIDATION](VALIDATION.md)。
